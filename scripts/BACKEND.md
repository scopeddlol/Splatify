# Splatify Backend

Use Node.js 22 and PostgreSQL 17 to match CI/containers (backend minimums: Node.js 20.9+ and PostgreSQL 14+). Uses `pg`, `zod`, and `sharp`, with raw SQL. No SMTP, external auth service, object storage, or ORM is required.

## Environment

- `DATABASE_URL`: PostgreSQL connection URL. Use a dedicated database and least-privilege application credentials. Configure verified database TLS via the connection URL when connecting remotely; TLS verification is never disabled in code.
- `APP_URL`: canonical public origin, such as `https://splatify.example.com`. Recommended in production, required when the reverse proxy changes the Host header. Actions reject missing or foreign Origin headers in addition to Next.js action protections.
- `ADMIN_EMAIL`: owner email, normalized to lowercase. Reserved from public signup. Admin access requires both this email match and the persisted `admin_verified` flag, which now denotes an environment-managed account.
- `ADMIN_NAME`: owner display name, 1-80 characters. Synced from the environment on each migration/startup.
- `ADMIN_PASSWORD`: private owner password, 12-128 characters, stored only as a salted scrypt hash in PostgreSQL. Use a unique randomly generated password. Whitespace is preserved. Quote values appropriately in `.env` and escape `$` as `\$` to prevent dotenv expansion. Never put real passwords into source control or command-line arguments.
- `TRUST_PROXY=1`: optional per-IP rate limiting. Enable only behind a trusted reverse proxy that strips and replaces the incoming `X-Forwarded-For` header. Otherwise requests share a conservative global database-backed limit. Account and event limits apply independently.
- `TEST_DATABASE_URL`: optional disposable test database, with permission to create schemas. Integration tests create and remove a uniquely named schema and do not use `DATABASE_URL`.

Run `npm run db:migrate` before starting the app. The script loads Next.js `.env*` files with `@next/env`, uses a transaction-scoped advisory lock, and records versioned migrations atomically in `schema_migrations`. Repeat runner invocations are safe; do not repeatedly execute the migration SQL by hand. Re-running the script also deletes expired sessions, expired rate-limit buckets, and activity older than 180 days. Schedule it daily, serialized with deployments. Back up PostgreSQL regularly.

## Schema Upgrades

- Version 1 is `src/lib/schema.sql`, the original users/auth, events/guests, schedule, gear, announcements, polls, activity, and rate-limit schema. Do not edit an already applied migration to upgrade a deployment.
- Version 2 is `src/lib/migrations/002-planning.sql`, applied by `scripts/migrate.ts` after version 1. It additively introduces profile fields, `media` with PostgreSQL `bytea` image data, location/visibility/custom invitation fields, `event_organizers`, `teams`, guest approval/team references, and `messages`, with supporting indexes and foreign keys.
- Existing events receive `visibility='private'` and `member_invites_enabled=true`; existing guests receive `approval='approved'`. Distinct nonempty legacy `guests.team` names are copied into per-event team records and linked through `team_id`. The legacy text column remains and team mutations keep it synchronized. The composite guest/team foreign key prevents cross-event assignments.
- Fresh databases receive both versions; upgrades preserve existing users, invitations, RSVPs, and planning data. Back up first and migrate before serving v2, whose reads require the new columns. Image rollback does not reverse migration 2. Keep the migration-before-web, admin synchronization, CI, and restore procedures in [README.md](../README.md).

## Environment Administrator

All three admin variables are required when `NODE_ENV=production`. Outside production, omitting all three (or leaving all three empty) prints a warning and disables any previously managed admin. Partial or invalid configuration always fails without making database changes. Set `NODE_ENV=production` for standalone production migrations. `scripts/start.ts` sets it automatically.

Provisioning runs inside the migration transaction on every invocation, even when both schema versions are already applied. It creates the configured account without using public signup, regardless of the registration setting. Existing trusted `admin_verified=true` accounts from the previous provisioning mechanism are adopted as environment-managed; their name and password are synchronized and legacy recovery codes removed. Admin provisioning itself needs no additional schema change.

- An existing ordinary account with the configured email causes an explicit refusal and a rollback of the entire transaction. It is never promoted, overwritten, or deleted. Choose an unused email or resolve the collision through a separately authorized database administration process. Changing back to a previously demoted account's email also triggers this refusal.
- Changing `ADMIN_EMAIL` creates a new managed account and demotes the old one, revoking the old account's sessions and recovery codes in the same transaction. Existing events remain owned by the old, now ordinary account; provisioning does not transfer or delete user data. Demotion does not erase the old password hash or prevent ordinary-account login.
- Changing `ADMIN_PASSWORD` updates the scrypt hash and revokes all sessions and recovery codes for that account. An unchanged password preserves the stored hash and sessions, including on concurrent/repeated provisioning runs. Name-only changes also preserve sessions. Managed accounts never retain recovery codes.
- Environment-managed accounts cannot use public password recovery, even if their email no longer matches the running environment before synchronization. Change the password in `.env` and rerun migration/restart instead. No setup-token signup field or public admin creation path remains.
- Keep the environment consistent across all app instances. Apply environment updates and run provisioning before accepting requests; do not run replicas with conflicting admin configuration.

`npm start` is wired to `tsx scripts/start.ts`. This wrapper forces production configuration, runs migration/provisioning, and starts Next only if migration succeeds; it requires `tsx` at runtime. It can also be invoked directly as `npx tsx scripts/start.ts` with optional Next start arguments. The standalone Docker image instead runs `node server.js`; Compose and deployment run the separate migration service before replacing web. Keep that order unchanged.

## UI Contract

Types live in `src/lib/types.ts`; reads in `src/lib/data.ts`, `src/lib/auth.ts`, and `src/lib/player-days.ts`; planning/auth actions in `src/app/actions.ts`; profile/image actions in `src/app/profile/actions.ts`; image processing in `src/lib/profile.ts`. Reads opt out of static rendering via `connection()` directly or through authentication; do not wrap them in shared caches. The app must run on the Node.js runtime, not Edge.

- Ordinary signup requires name, email, and a 12-128 character password, plus an optional allowlisted local `next` return path. Signup redirects to `/recovery-codes`; `getRecoveryCodes()` returns eight recovery codes for the current authenticated session, for up to ten minutes. The return destination is encrypted in a session-bound HttpOnly cookie and consumed by `acknowledgeRecoveryAction`, defaulting to `/dashboard` if absent/invalid/expired. Login and recovery also validate `next`. Render codes privately; the display cookie is cleared on acknowledgement, login, logout, or recovery. Plaintext codes are never persisted in PostgreSQL. Each code works once, and password recovery revokes all previous sessions. The environment admin signs in directly and receives no recovery codes.
- Invite pages are bearer-link accessible. Do not publish them in sitemaps or analytics. Configure the UI's robots and referrer policy to avoid link leakage, especially for personal edit links.
- An RSVP sets an event-specific HttpOnly edit cookie and redirects to `/days/{eventId}`. `EventDetail.guestEditToken` is returned only for the current unlinked guest. New personal links use `/rsvp/{eventId}?editToken={guestEditToken}`, independent of invitation rotation. The legacy `/invite/{inviteToken}?editToken=...` route remains valid only while its invitation token is valid. Both render explicit confirmation forms for `claimGuestAction`, which validates an unlinked RSVP, sets the cookie, and redirects to the clean day URL. Never claim on GET. Anyone holding a valid unlinked personal link can edit its RSVP; keep it private.
- Signed-in RSVPs link to the account and appear in attending lists and `getMyInvitations()`. Saving an unlinked guest RSVP while signed in links it; claiming a link alone does not. Account identity takes precedence over guest cookies, and cookies/personal links only authorize rows with `user_id IS NULL`. Linked RSVPs therefore become account-only, including across devices. Poll voting uses account identity or an unlinked guest cookie and requires approved, non-declined attendance, not necessarily an edit cookie. Names and email text never identify an RSVP.
- `capacity=0` means unlimited confirmed players, with a 1,000-total-guest safety cap including pending requests. Only approved going RSVPs consume capacity; approval and RSVP changes lock the event and recheck capacity. Owned events are capped at 100; schedules, gear, announcements, and teams at 100 each; polls at 50 with 2-6 options; messages at 10,000 per day and 2,000 characters each. Admin lists are capped at 50. Legacy `getMyEvents()`/`getMyInvitations()` reads use 100-row pages, not the dashboard's 12-row pages.
- Gear `cost` is the estimated cost per player for that line. Sum `cost` across gear items; do not multiply by `quantity`.
- Invite rotation by an owner or co-organizer invalidates the old invite URL, not existing account access, guest cookies, or event-ID personal edit links. Share the new invitation URL for new invitees. Guest edit tokens and sessions are hashed in PostgreSQL; event invitation tokens remain retrievable for authorized sharing, but are scrubbed from public discovery, dashboard cards, and unauthorized member detail/list results.
- All mutations redirect with a safe `?error=` or `?success=` message, or to the created event/auth destination. Actions revalidate the root layout to invalidate dashboard, event, invite, settings, and admin views. Surface query messages as escaped React text, never HTML.

## Routes And Access

- `/explore` calls `getPublicEvents({ city, state, query, page })`: public days dated today or later or undated, 12 per page. City and title/description/venue keyword matching are case-insensitive substrings. `regionSearchTerms()` normalizes surrounding whitespace/case and matches US full state names and abbreviations (all 50 states plus DC) against either stored form; other regions use case-insensitive exact matching.
- `/dashboard` calls `getPlayerDays(view, page)`, with 12-row attending and organizing pages. Attending includes all account-linked RSVPs, including pending or declined ones; organizing includes ownership and co-organizer membership. No guest cookie is needed for linked attendance.
- `/days/{id}` and its `overview`, `players`, `schedule`, `gear`, `messages`, and `settings` sections use `getDay()`. Private days require an organizer or a current RSVP; a valid bearer invitation uses `getSharedEvent()` at `/invite/{token}`. Settings require organizer access. Roster/planning data requires organizer access or approved attendance; rosters and messages use 20-row pages.
- Public posting is opt-in, defaults to private, and requires city and state/region. Public previews reveal event details (including exact venue/address and covers), approved going totals/availability, and the exact aggregate estimated per-player cost. They contain no guest rows, player profiles, messages, itemized gear, schedules, announcements, or polls. `realName` is never selected into roster/player-card data. Public visibility does not imply public membership data.
- `memberInvitesEnabled=false` is an approval gate for **all new non-organizer requests**, public or private, accountless or signed-in, including requests arriving through an organizer-shared link. Existing approval values are preserved, so approved players remain approved and pending players remain pending. Owners and co-organizers approve or remove requests; organizer RSVPs are approved directly.
- When the toggle is off, members lose invitation issuance/share UI and receive no raw invitation token in their day/list data. Organizers still have sharing controls. This cannot un-forward bearer links already distributed: their holders can still open the invitation and submit a pending request. Rotate the invitation to invalidate old URLs; disabling the toggle alone is not revocation.
- Co-organizers can manage all day planning, settings/images, invitations, approvals, schedules, gear, announcements, polls, teams/captains, and message moderation. Only the original owner can add/remove co-organizers or delete the day through planning actions. Co-organizer appointments must select approved registered non-declined players. Site-admin deletion is a separate administrative capability.
- Captains must be approved registered non-declined players. They can rename/recolor their own team, add approved non-declined unassigned players, and release their own players. They cannot move someone out of another team or change captain appointments. Organizers can assign across teams and appoint captains.
- Message reads/posts require organizer access or signed-in, account-linked, approved non-declined attendance. Approved accountless guests see a sign-in/link prompt, not messages. Authors may delete their own messages; organizers may delete any day message. Sending is limited to 20 messages per user per minute in addition to general action limits.
- `/profile` uses `saveProfileAction`: display name (`users.name`, 1-80 characters), private `realName` (up to 120), bio (up to 500), mechanical/electric/rental default marker, and avatar replacement/removal. Admin display names remain managed by `ADMIN_NAME`. Profile defaults do not rewrite existing RSVP names/markers.

## Media And Manifest

`processImage()` in `src/lib/profile.ts` accepts still JPEG, PNG, or WebP uploads up to 4 MiB, verifies decoded format using `sharp` rather than filename/MIME claims, and rejects multi-page or corrupt files and inputs over 20,000,000 decoded pixels. It auto-orients, strips metadata, resizes inside 512x512 for avatars or 1600x1600 for day/invitation covers without enlargement, and re-encodes WebP at quality 80. Processed data is also bounded to 4 MiB. `next.config.ts` sets the server-action body limit to `6mb` for multipart overhead; that does not increase the per-image limit. Check proxy request limits separately.

`saveImage()` runs inside the caller's authorized transaction, locks the destination, links the replacement, and removes superseded images. Profile actions authorize self-access; event image upload/removal allows owners and co-organizers. Images are stored in `media.data` as PostgreSQL `bytea`, not on disk or in an external service. No storage credentials or extra persistent upload volume are needed. Normal PostgreSQL backups/restores include avatars and covers; budget database and backup capacity accordingly.

The same-origin `GET /media/{id}` route checks authorization before returning WebP with `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`; inaccessible/missing images return 404. Public visibility or a valid `inviteToken` query grants event cover/invitation image access, never roster/avatar access. Current attendees (including pending ones) can view event covers. Avatars require self-access or authorized shared-day roster access; organizers can also view pending players' avatars. Linked account attendance takes precedence over unlinked cookies here too. Do not cache this route at a CDN or add shared/private offline caches.

`src/app/manifest.ts` supplies standalone-display metadata with `/explore` as its start URL. `public/mark.svg` is the favicon and source for PNGs generated by `/icons/{size}` at 180, 192, and 512 pixels. Apple uses 180; manifest icons use 192/512, including a maskable 512 entry. Generated public icons are publicly cacheable, unlike uploaded media. No service worker, offline private-data cache, notifications, automatic waitlist, or calendar downloads are implemented; those are potential future recommendations, not backend capabilities.

## Verification

Run `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`. Unit tests include validation, security/auth return paths, provisioning, presentation/state matching, and image decoding/limits. Database, planning, and media-access integration tests skip unless `TEST_DATABASE_URL` is explicitly exported; `npm test` does not load `.env` for you. Use a disposable database with schema-creation privileges: tests create and remove temporary schemas, not production data. Tests exercise migrations, capacity/recovery concurrency, provisioning, planning roles/approval/privacy, and media authorization. These checks do not replace real-browser verification of cookies, redirects, CSRF, and UI controls. CI provides its disposable PostgreSQL service and explicit test environment; browser tooling is not added to the application dependency set.

`tests/browser-smoke.ts` and `tests/ui-smoke.ts` are separate opt-in real-browser scripts, currently being updated for the v2 routes and UI. Their existence is not evidence that v2 browser journeys passed. Inspect the current scripts for fixture and selector requirements before running; do not run them against production or claim coverage for unfinished scenarios.

- Export `BROWSER_DATABASE_URL` for an already migrated disposable database. The running test app's `DATABASE_URL` must point to that same database; this is distinct from schema-isolated `TEST_DATABASE_URL` testing.
- Export `BROWSER_BASE_URL` for that running app (default `http://127.0.0.1:3107`), with a matching `APP_URL`. Use the development server for plain HTTP because production cookies require HTTPS.
- Export `PLAYWRIGHT_MODULE` as a resolvable module/path to an external Playwright installation and `BROWSER_EXECUTABLE` as the path to Chromium/Edge. The scripts use that executable; they do not install browsers or start the app.
- For `tests/ui-smoke.ts`, also export `UI_SCREENSHOT_DIR` pointing to an existing writable screenshot directory outside committed source. Its browser contexts include desktop and mobile viewports.
- Current disposable admin fixtures use `ADMIN_EMAIL=admin@splatify.test`, `ADMIN_NAME=Local Admin`, and `ADMIN_PASSWORD=local-only-splatify-admin`. Provision those only in the isolated test app/database, never production. Tests mutate data and may leave admin sessions/activity even after fixture cleanup; discard the database afterwards.

With those process environments configured, run the scripts separately:

```sh
npx tsx tests/browser-smoke.ts
npx tsx tests/ui-smoke.ts
```

These are not run by `npm test` or the existing CI unit/integration command. Keep external browser configuration optional; no production storage, deployment, or credential changes are needed for v2 media.
