# Splatify Backend

Requires Node.js 20.9+ and PostgreSQL 14+. Uses the existing `pg` and `zod` dependencies. No SMTP, external auth service, or ORM is required.

## Environment

- `DATABASE_URL`: PostgreSQL connection URL. Use a dedicated database and least-privilege application credentials. Configure verified database TLS via the connection URL when connecting remotely; TLS verification is never disabled in code.
- `APP_URL`: canonical public origin, such as `https://splatify.example.com`. Recommended in production, required when the reverse proxy changes the Host header. Actions reject missing or foreign Origin headers in addition to Next.js action protections.
- `ADMIN_EMAIL`: owner email, normalized to lowercase. Reserved from public signup. Admin access requires both this email match and the persisted `admin_verified` flag, which now denotes an environment-managed account.
- `ADMIN_NAME`: owner display name, 1-80 characters. Synced from the environment on each migration/startup.
- `ADMIN_PASSWORD`: private owner password, 12-128 characters, stored only as a salted scrypt hash in PostgreSQL. Use a unique randomly generated password. Whitespace is preserved. Quote values appropriately in `.env` and escape `$` as `\$` to prevent dotenv expansion. Never put real passwords into source control or command-line arguments.
- `TRUST_PROXY=1`: optional per-IP rate limiting. Enable only behind a trusted reverse proxy that strips and replaces the incoming `X-Forwarded-For` header. Otherwise requests share a conservative global database-backed limit. Account and event limits apply independently.
- `TEST_DATABASE_URL`: optional disposable test database, with permission to create schemas. Integration tests create and remove a uniquely named schema and do not use `DATABASE_URL`.

Run `npm run db:migrate` before starting the app. The script loads Next.js `.env*` files, uses an advisory lock, and records versioned migrations atomically. Repeat runs are safe. `schema.sql` is migration version 1; add a new migration version rather than changing an already deployed schema. Re-running the script also deletes expired sessions, expired rate-limit buckets, and activity older than 180 days. Schedule it daily for maintenance. Back up PostgreSQL regularly.

## Environment Administrator

All three admin variables are required when `NODE_ENV=production`. Outside production, omitting all three (or leaving all three empty) prints a warning and disables any previously managed admin. Partial or invalid configuration always fails without making database changes. Set `NODE_ENV=production` for standalone production migrations. `scripts/start.ts` sets it automatically.

Provisioning runs inside the migration transaction on every invocation, even when schema version 1 is already applied. It creates the configured account without using public signup, regardless of the registration setting. Existing trusted `admin_verified=true` accounts from the previous provisioning mechanism are adopted as environment-managed; their name and password are synchronized and legacy recovery codes removed. No schema change is needed.

- An existing ordinary account with the configured email causes an explicit refusal and a rollback of the entire transaction. It is never promoted, overwritten, or deleted. Choose an unused email or resolve the collision through a separately authorized database administration process. Changing back to a previously demoted account's email also triggers this refusal.
- Changing `ADMIN_EMAIL` creates a new managed account and demotes the old one, revoking the old account's sessions and recovery codes in the same transaction. Existing events remain owned by the old, now ordinary account; provisioning does not transfer or delete user data. Demotion does not erase the old password hash or prevent ordinary-account login.
- Changing `ADMIN_PASSWORD` updates the scrypt hash and revokes all sessions and recovery codes for that account. An unchanged password preserves the stored hash and sessions, including on concurrent/repeated provisioning runs. Name-only changes also preserve sessions. Managed accounts never retain recovery codes.
- Environment-managed accounts cannot use public password recovery, even if their email no longer matches the running environment before synchronization. Change the password in `.env` and rerun migration/restart instead. No setup-token signup field or public admin creation path remains.
- Keep the environment consistent across all app instances. Apply environment updates and run provisioning before accepting requests; do not run replicas with conflicting admin configuration.

For startup provisioning after `npm run build`, run `npx tsx scripts/start.ts` (optional Next start arguments follow it). This wrapper runs migration with production configuration and starts Next only if migration succeeds. It requires the existing `tsx` package at runtime. The wrapper is not wired into `package.json`, which is owned by the main implementation; set the deployment start command to this wrapper, or run migration as a mandatory step before `npm start`. Plain `npm start` is not changed by this backend patch.

## UI Contract

All specified types and data functions are exported from `src/lib/types.ts` and `src/lib/data.ts`. All specified actions are exported from `src/app/actions.ts`. Data reads opt out of static rendering via `connection()`; do not wrap these exports in shared caches. The app must run on the Node.js runtime, not Edge.

- Ordinary signup requires a 12-128 character password and accepts only name, email and password. Signup redirects to `/recovery-codes`; `getRecoveryCodes()` returns eight recovery codes for the current authenticated session, for up to ten minutes. Render privately and provide a form for `acknowledgeRecoveryAction`. The encrypted HttpOnly display cookie is cleared on acknowledgement, login, logout, or recovery; plaintext codes are never persisted in PostgreSQL. Codes remain readable during the short acknowledgement window so reloads do not lose the only copy. There is no email recovery. Each code works once, and password recovery revokes all previous sessions. The environment admin signs in directly and does not receive recovery codes.
- Invite pages are bearer-link accessible. Do not publish them in sitemaps or analytics. Configure the UI's robots and referrer policy to avoid link leakage, especially for personal edit links.
- An RSVP sets an event-specific, HttpOnly edit cookie and redirects to the invite page. `EventDetail.guestEditToken` is provided only when that cookie matches `currentGuest`. The UI can show a personal link `/invite/{inviteToken}?editToken={guestEditToken}`. The target page should render a confirmation form posting `inviteToken` and `editToken` to `claimGuestAction`; do not mutate cookies during server rendering or automatically claim on GET. The action redirects to the clean invite URL. Anyone with the personal link can edit that RSVP, so label it private.
- Signed-in RSVPs link to the account and appear in `getMyInvitations()`. Submitting another RSVP from the same account reclaims its existing linked RSVP and issues a new edit token if the cookie was missing. Poll voting still requires the edit cookie. Names and email text never identify an RSVP.
- `capacity=0` means unlimited confirmed players, with a 1,000-total-guest safety cap. Event lists and owned events are capped at 100; schedules, gear, and announcements at 100 each; polls at 50, with 2-6 options each. Admin lists are capped at 50.
- Gear `cost` is the estimated cost per player for that line. Sum `cost` across gear items; do not multiply by `quantity`.
- Invite rotation invalidates the old invite URL; existing guest edit cookies remain usable at the new invitation URL. Owners must share the new URL. Guest edit tokens and sessions are hashed in PostgreSQL; event invite tokens are intentionally retrievable so owners can share them.
- All mutations redirect with a safe `?error=` or `?success=` message, or to the created event/auth destination. Actions revalidate the root layout to invalidate dashboard, event, invite, settings, and admin views. Surface query messages as escaped React text, never HTML.

## Verification

Run `npm test` and `npm run typecheck`. Unit tests cover environment validation, safe provisioning errors, unchanged/name-only/password-change behavior, collision refusal, demotion, and public-recovery restrictions. Database integration tests skip unless `TEST_DATABASE_URL` is explicitly set. The integration suite checks schema repeatability, concurrent capacity locking, single-use recovery consumption, poll foreign keys, cascade cleanup, concurrent admin provisioning, collision rollback, password rotation, email rotation, and removal of local admin configuration. It does not replace end-to-end browser tests for cookies, redirects, CSRF, or UI ownership controls.

`tests/browser-smoke.ts` is a separate opt-in real-browser test. Set `BROWSER_DATABASE_URL` to an already migrated disposable database, `BROWSER_BASE_URL` to its running app (default `http://127.0.0.1:3107`), `PLAYWRIGHT_MODULE` to an external Playwright installation, and `BROWSER_EXECUTABLE` to a Chromium/Edge executable. Run `npx tsx tests/browser-smoke.ts`. Its disposable administrator fixture uses `ADMIN_EMAIL=admin@splatify.test`, `ADMIN_NAME=Local Admin`, and `ADMIN_PASSWORD=local-only-splatify-admin`; never use these credentials in production. The test covers signup, recovery-code display/acknowledgement, event creation, private-page authorization, RSVP editing, capacity rejection, personal-link claiming, admin login, and a forged event-ID mutation. It deletes its temporary organizer and events but leaves administrator login sessions and activity records in the disposable database.
